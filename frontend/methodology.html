Methodology

The SimplyWins standard.

A benchmark only matters if the decision can be reproduced. The backend must preserve the contract below rather than simply returning a preferred model.

⚖
Decision rule

The winner is the lowest-complexity method that satisfies every required constraint.

If no method passes, the system returns “no passing method” instead of forcing a winner.

01

Define the operating requirement

Set the minimum acceptable quality and the limits on cost, latency, volume, auditability, and reliability before benchmarking.

02

Build the cheapest credible baseline first

Start with deterministic rules. Then add traditional ML, smaller models, and frontier models only when the task justifies them.

03

Evaluate on the same task and dataset

Every method must see the same inputs and be judged against the same labels or assertion-based success criteria.

04

Separate measured facts from estimates

Accuracy and latency come from benchmark runs. Cost can be computed from provider pricing, but every result stores its provenance and version.

05

Recommend by constraint, not hype

Among methods that pass all active constraints, choose the one with the lowest complexity rank.

06

Keep every run reproducible

Dataset version, code commit, method configuration, model name, provider, prompt, and run timestamp must be saved with every result.

01

Performance

Accuracy, task success, latency, throughput, and error rate.

02

Economics

Cost per 1K tasks and projected cost at the selected operating volume.

03

Control

Determinism, auditability, reproducibility, privacy, and maintenance burden.

04

Complexity

Rules → traditional ML → small model → frontier LLM, unless the benchmark documents a different hierarchy.

Frontend status
