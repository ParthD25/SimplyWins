## What this is

Short customer support messages labelled with the queue they belong in. It
exists to compare implementation classes on identical data, not to represent
any particular company's support traffic.

Regenerate and verify the checksum with:

```bash
python -m app.benchmarks.datasets.support_ticket_routing.generate
```

## How it is built

150 hand-written phrasings (30 per class) with slot substitution for amounts,
dates, products, names, and places. Roughly 40% of examples are deliberately
hard:

| Difficulty | Share | What it tests |
| --- | --- | --- |
| `plain` | ~59% | Baseline phrasing |
| `multi_intent` | ~15% | Mentions a second queue; label is the primary intent |
| `sparse` | ~10% | Truncated to a few words |
| `negation` | ~7% | Explicitly denies a category it mentions |
| `typos` | ~7% | Character substitutions |

Classes deliberately share vocabulary — "account" appears in billing tickets
("bank account"), "order" in both shipping and billing — so keyword matching
cannot trivially separate them.

## The split is template-disjoint

**Each phrasing appears in either train or test, never both.** A class's 30
templates are partitioned 60/40, and examples are generated only from the
templates belonging to their split.

This matters more than it sounds. An earlier version used a random split, and a
character n-gram model scored **98.75%** — it had memorised phrasing
fingerprints, because 72% of test examples shared their opening six words with
a training example. That number measured recall of the generator, not
generalisation. Under the template-disjoint split the same model scores 89.5%,
which is a claim about unseen wording.

## Known limitations

Read these before citing any number from this dataset.

1. **It is synthetic.** Difficulty is a property of this generator. Results here
   do not transfer to production support traffic without re-measurement.
2. **The class balance is artificial.** Real queues are heavily skewed; this is
   uniform, which flatters macro-averaged metrics.
3. **The generator and the keyword rules were written by the same author.** The
   rule vocabulary was chosen from general support-domain language rather than
   from the generator's templates, but this is not the same guarantee as an
   independently sourced dataset.
4. **Template pool is finite.** 30 phrasings per class is far less lexical
   variety than real traffic, so the gap between methods may compress or widen
   on real data.
5. **No small-model or frontier-LLM result exists.** Those method classes are
   unimplemented, so this dataset currently supports a two-way comparison only.

The honest summary: this is enough to validate the runner, the metric, and the
provenance pipeline end to end, and to give a directional read on rules vs
traditional ML. It is not enough to make a strong claim about the task in
general. Replacing it with a real, licensed corpus is the next meaningful step.
